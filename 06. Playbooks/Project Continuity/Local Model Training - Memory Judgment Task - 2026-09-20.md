## Carried-Forward Traps (paid for by the Hermes runs; do not rediscover)

Environment, from that rig's `SETUP.md`:
1. `device_map="auto"` **cannot** load this model 4-bit on this GPU — accelerate plans on BF16 sizes (17.98 GiB) and offloads quantized modules to CPU, which bnb rejects. Use `device_map={"": 0}`.
2. `prepare_model_for_kbit_training()` **OOMs an 8 GB card** (upcasts embed_tokens, 1.01B params, +2 GB). Do it manually: freeze all params, upcast only `*norm*` modules, gradient checkpointing with `use_reentrant=False`.
3. Set `use_cache=False` explicitly.
4. Hybrid attention needs extra LoRA targets: 24 of 32 layers are gated-DeltaNet. Include `in_proj_qkv`, `in_proj_z`, `in_proj_a`, `in_proj_b` alongside `q/k/v/o` and `gate/up/down`.
5. After any driver-level OOM, the allocator's expandable-segments path is fragile — eval with `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:False`.
6. Long records OOM this card: at 248k vocab the fp32 cross-entropy peak scales with `seq_len × vocab`; a 1,188-token record killed a run. Cap input at the dataset level and fail fast rather than truncating answer tokens.

Methodology, from the recorded results:
7. **Dataset size decides the outcome, not hyperparameters.** Hermes `state_extraction` had 4 training records against a 0.85 bar and never moved (0.286 → 0.286 at v1; 0.20 → 0.40 at v3). Its `gate_outcome` had 40 and improved reasons-F1 0.60 → 0.867.
8. **Audit derivability before training.** Hermes v1 asked for three fields that appeared in the input 0 times out of 9 — it was training fabrication. Every target field must be provably present in the input.
9. **One adapter per task family.** v3 proved cross-task interference: a null-heavy task taught an "emit nothing" prior that collapsed gate status accuracy 1.00 → 0.60.
10. **Saturated baselines cannot carry an improvement gate.** Measure the base model first and pick metrics with headroom.

## Retrieval miss diagnosis — why precision@1 is 0.629

Tools: `tmp/ft-retrieval-miss-diag.py`, `tmp/ft-retrieval-rerank-sim.py`, `tmp/ft-mcnemar.py`. 75 misses analysed (cases where the used doc was not rank 1).

**Root cause: no recency prior.** Where both docs were dated, the doc actually used was **newer than the wrongly top-ranked doc 34 times vs older 9** (5 same-date). Veritas's queries are overwhelmingly current-state ("status", "current", "pending", "next action"), but the index scores a 2026-08-08 chunk and a 2026-09-19 chunk purely on similarity.

Simulated fix `score' = score + w · 1/(1 + age_days/30)`, recency computed against the query's own date so no future information leaks. Tuned on the older 60% of pairs, scored on the held-out newer 40% (n=84):

| Weight | Held-out p@1 | McNemar (fixed / broke) |
|---|---|---|
| 0 (baseline) | 0.631 | — |
| 0.15 | 0.679 | 5 / 1, p=0.221 (n.s.) |
| 0.5 | 0.762 | 14 / 3, **p=0.015** |
| 1.0 | 0.774 | 17 / 5, **p=0.019** |
| 20 (≈pure recency) | 0.691 | — |

**The effect is real but the weight is not identifiable.** Performance peaks at an interior optimum (w≈1.0) and *declines* toward pure recency, so this is a genuine blend signal, not a degenerate "always pick newest". However the tune split selected w=20 while the test split peaks at w=1.0 — the two disagree, which means 210 pairs cannot pin the constant. Honest caveat: w=0.5/1.0 were examined after seeing the test curve, so only the direction (every w>0 beats w=0 on both splits) is free of selection bias.

**Secondary findings:** lexical dominance — wrongly-top chunks often carry textScore 0.83–0.98 while the genuinely useful chunk had textScore 0 (46/210 used docs scored 0 on text), so BM25-style keyword matches outrank semantically better material. Chunk size is a weak contributor (tiny ≤3-line chunks are 29/75 of wrong tops vs 20/75 of used docs) and is *not* the main driver. 29/75 misses sit within a 0.05 score margin — reranking territory rather than recall failure.

**Not actionable as config.** No recency, weighting, or ranking knob exists in the documented `concepts/active-memory/*` surface; the query-side `tuning.md` controls only context mode/profile. A real fix is an upstream OpenClaw change, not a local setting — **do not attempt a config edit for this.**

**Already partly mitigated by doctrine:** `AGENTS.md` startup step 3 tells Veritas to read today's/yesterday's memory directly rather than relying on semantic rank. That instruction is compensating for exactly this defect; the diagnosis explains why it earns its place.

**Ordering constraint:** changing the ranker invalidates every pair collected under the old one, resetting the 213-pair count toward the retriever-training threshold. Decide ranking changes *before* accumulating more pairs, not after.
