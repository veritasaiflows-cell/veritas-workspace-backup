# Performance And Disk-Mass Review

Read when the request asks how fast or how heavy the workspace is - workspace, memory, routing, search or startup latency, "what is slow", disk growth, or a storage-mass finding - before proposing any optimization. This is a measurement review: it produces attributed findings and owner-gated recommendations, never an applied change.

1. **Establish the process-spawn floor before judging any route.** Measure it rather than assuming, and measure a native non-Python control alongside it: a bare `python -c pass`, `python -S -c pass`, `python -I -S -c pass`, and a native executable such as `git --version`. Take an N-run median; single runs on this host swung 1,348-3,939 ms for identical commands, so one run is not a measurement. Verified 2026-09-22 on this host: `python -c pass` median 1,985 ms, `python -I -S -c pass` 1,487 ms, native `git --version` 1,469 ms, `where.exe` 886 ms - a native binary costs about the same as the interpreter, and skipping site init saves only ~120 ms with `sitecustomize.py` and `usercustomize.py` both absent. **The floor is host process creation, not interpreter init**, so attribute it to the platform and do not propose interpreter-level tuning. A route measuring 1.4-2.0 s is largely process creation, and a turn that spawns several scripts pays that floor once per process: count the spawns and name the batching or chain-consolidation target before optimizing the work. **Done:** the floor, a native control and the route time are all stated with the N-run median, and the spawn count for the turn is named. The earlier 364-494 ms bare-Python floor recorded for this host is superseded and must not be reused.

2. **Attribute a slow model-backed path to its layer before calling it slow.** Measure the same operation cold and warm, time the backing service on a trivial request, and separate the cost of *transport* from the cost of *work*. Replicate the real transport, not just the query: an in-process replica of the same retrieval steps gets OS page cache and warm in-process state and will look fast while the production path pays a per-call process cost. **Done:** each layer's time is measured, transport is separated from work, and the slow layer is named.

   Verified, including a corrected first answer (2026-09-20, two passes). `memory_search` end-to-end 4,123 ms was first decomposed as manager 1,872 plus search 2,248 and attributed to the embedding layer, with warm-up/keep-alive named as the fix. That was **wrong**: with the model provably resident, `searchMs` held at 2,660-3,440 ms. The true decomposition came from replicating the transport - a full end-to-end replica totalling 1,885 ms, of which **1,662 ms was an out-of-process KNN child spawn paid on every query** (`manager.searchVector` -> `runVectorKnnInSubprocess` -> `spawn(process.execPath, [.../memory-search-knn.child.js])`). A fresh in-session read agreed (`searchMs` 1,776, `toolMs` 1,790). A cold embedding load is real (~2.7 s) but one-time, and covered by keep-alive only while that keeper is verified to act ([automation recovery](automation-recovery-proof.md) step 15); it is not the warm-recall cost.

   - Time a **startup-only control** when the path includes a worker or child process, to split process creation from work: a no-op child and a real KNN child measured 1,306-1,608 ms against 1,553-1,744 ms, so ~1.2-1.4 s of the spawn was process creation rather than the query.
   - Attribute a process-creation term to the platform, not to Node initialization: `node --version` and `node -e 0` cost the same (~1,355 against ~1,254 ms), and `--no-warnings`, `--jitless` and a larger heap changed nothing.
   - Size the **working set**, not the file. The KNN step touches ~44 MB (30.5 MB of vectors plus 13.1 MB of text across 10,396 chunks), not the store's 1,871 MB, so a "1.8 GB store" premise predicts disk cost that the scan never incurs.
   - A/B a tuning hypothesis at the **real** parameter width. `mmap_size`/`cache_size` sat at SQLite defaults (0 / 2 MB) and raising them cut KNN from 130-138 ms to 22-36 ms at k=480 - real, but ~5% of the observed total, not the residual. The width is `min(200, maxResults * candidateMultiplier)` (`manager-runtime.js:5442`), ~60 candidates at defaults, times the 8x oversample factor. Report each pragma in its own units: a negative `cache_size` is a KiB count, not pages, so a `cache_size * page_size` product overstates it (`-2000` is 1.95 MB, not the 7.8 MB that product gives).
   - Confirm a config surface exists before proposing a config change: a full scan of the installed `dist` found **no** `mmap_size` setting and no memory-search `cache_size`, so the only local form of that change is an edit inside installed `node_modules`, which the next upgrade overwrites. Name the upstream ask instead of proposing a patch that cannot survive.
   - Before escalating that platform-attributed cost upstream, prove the ask is still open. Search the tracker for the symptom; if a related issue exists and is closed, read its fix PR and verify whether that fix is present in the installed build. Verified 2026-09-21: a same-symptom issue (a throwaway KNN child booting per query) was already closed by an import-slimming PR whose matched Linux proof was child boot 443 to 60 ms and which **is** present in the installed `dist`; a re-measured bare-boot control (`node --version` median 1,696 ms against the real child 1,778 ms) showed no measurable module-graph penalty left, so the residual was process creation - the one term that fix never targeted. File that as a **new** issue cross-referencing the closed one, never as a reopen and never as a comment on the closed thread, which rarely re-enters triage. Verify a scope claim against the runtime condition rather than a comment: the spawn path's "file-backed" qualifier traces only to code comments while the KNN wiring is unconditional, so the same path also applies to non-file-backed indexes. State platform-dependence in the write-up - here a Windows process-creation term worth ~60 ms per search on Linux after the fix - so upstream can judge severity rather than assume a universal regression. Deliver the write-up as a draft; filing is a separate external action under the Stop Lines. Then compare the fix's merge date against your build's release date, in both directions, because "fixed on main" is not "fixed here": a fix merged after the release you are running on is absent from your build no matter what the tracker reports. Before filing, that check reframes the report as a release-tracking note rather than a fresh defect. After filing, it is what makes an upstream closure adjudicable. Verified 2026-09-22: a report filed against installed 2026.9.4 (released 2026-09-11) was closed the next day as superseded by a process-reuse PR merged 2026-09-20, while the newest published release (2026.9.5, 2026-09-19) also predated that merge - so no released build contained the fix and the measured cost persisted on the reporting host. When a closure cites a merged fix, treat it as substantively correct about `main` and simultaneously not true for that host until the upgrade: verify the cited change actually addresses the ask filed (there it granted the primary ask and explicitly deferred the secondary one to separate evaluation), confirm the mechanism in the installed build rather than trusting the closure (the child was still one-shot, `process.stdin.once("end", ...)` with no request-id protocol), report the user-visible state against the installed build, and name the first release to watch for instead of reporting the item as fixed.

3. **Profile an outlier front door instead of guessing at it.** Order the candidate routes by measured time, take the one an order of magnitude off its peers, and read a profile (call counts plus internal time) before prescribing anything. Verified: `db_lifecycle_manifest.py --validate` ran 6,049-8,129 ms against 417-862 ms peers; its profile showed 3,057,280 calls dominated by `nt.stat` (1.721 s over 40,310 calls) and recursive glob, i.e. stat and glob fanout rather than data volume. **Done:** the dominant call site and its call count are named, or the outlier is reported as unexplained.

4. **Check compaction headroom before recommending a vacuum or compaction.** Read free pages against total pages; near-zero means the store holds live data and compaction buys nothing. Verified: a 1,772 MB agent store carried a 19-page freelist (0.0%), so a vacuum recommendation would have been wasted work, while a store at 15.6% free does have reclaimable space. **Done:** the free-page share is quoted and the recommendation follows it.

5. **Verify a derived index's freshness and speed against the live alternative before trusting it as a retrieval surface.** Read the index's last-write time, count the files changed since, and time the index query against the direct search. Verified: `workspace-index.sqlite` was 40.6 h old with 908 files changed since its build and answered in 456-491 ms while a targeted `rg` answered in 280 ms, so the current-state route is the search, not the index. **Done:** staleness, drift count and both timings are recorded, and the recommended surface is named.

6. **Separate message admission, run preparation, global-lane wait and provider latency before blaming model startup.** Read the configured `agents.defaults.maxConcurrent`, then inspect a bounded recent Gateway-log window for `reply resolver timings`, `lane wait exceeded: lane=main`, `global_lane:waiting`, and provider-transport start/response pairs. Treat a session whose last progress is `global_lane:waiting` as queued, not model-stuck. Only after queue evidence exists, inspect active sessions and agent processes to identify the workload occupying the slots. Attribute time independently to preparation, global queue, provider connection and model generation when the logs expose them. If the global lane is saturated while provider responses remain fast, recommend reducing batch/evaluation concurrency enough to reserve an interactive slot before proposing a higher global cap; changing `maxConcurrent` is a separate config/runtime decision requiring current resource and rate-limit evidence plus approval. **Done:** the delay is assigned to a measured layer, the slot owner is named, and model/provider tuning is not proposed for queue time.

Report the largest disk consumers with their growth rate and cutoff, and for each one confirm an actual retention route exists rather than assuming the contract that names its directory covers it. Derive a growth rate from the file's own record timestamps sampled across its length, never from size divided by age: a lifetime average is diluted by earlier low-volume periods and by sibling files in the same directory, and it understated one live file by more than an order of magnitude (a size-over-age estimate of 9.6 MB/day against a measured 24.5 MB/hour), which inverts the cadence decision that depends on it. State the rate, the window it was measured over, and the projected volume at the retention window. Never present a task-time measurement as a standing value, and mark every repair owner-gated.
