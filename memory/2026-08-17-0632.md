## What `graphifyy[sql]` is for

- Adds `tree-sitter-sql` grammar support to graphify.
- Lets graphify parse `.sql` files via AST extraction (no LLM, no API key).
- Extracts: tables, views, functions/procedures, triggers, and relationships (`references`, `reads_from`, `triggers`, `contains`).

## What it does NOT do

- Does **not** index live databases directly (except PostgreSQL — see below).
- Does **not** read table rows / data contents.
- Does **not** support live SQLite, MySQL, SQL Server, etc.

user: What are the benefits of dumping schema to sql
assistant: Good question. The practical benefits of dumping a database schema to `.sql` before graphifying it:

## 1. Makes any SQL database graphifiable

graphify only has built-in live introspection for **PostgreSQL**. SQLite, MySQL, SQL Server, DuckDB, etc. have no live connector. Dumping to `.sql` is the universal adapter.

## 2. Schema-only = focused, safe graph

You get tables, views, functions, triggers, and foreign-key relationships without pulling in:
- row data
- PII / sensitive values
- large blobs
- transaction logs

This keeps the graph small and avoids data-privacy or security issues.

## 3. Captures cross-file / cross-database relationships

If your system spans multiple SQLite files or `.sql` migration scripts, dumping them into one graph shows relationships that live inside each DB alone would hide.

## 4. Version-controllable snapshot

A `.sql` dump is a static artifact you can diff, hash, and reproduce. That makes graph outputs auditable and comparable over time — useful for schema drift detection.

## 5. Works with graphify's existing code pipeline

`.sql` files are treated as **code** by graphify, parsed with AST (no LLM cost, no API key). You get deterministic extraction without semantic extraction overhead.

## 6. Normalizes dialect quirks

Dumpers usually produce standard-ish DDL. That lets graphify parse schemas from different engines using the same `tree-sitter-sql` parser, rather than needing per-dialect connectors.

## The main downside

The dump is a **point-in-time snapshot**. It's stale the moment the live schema changes. For always-current graphs, you'd need to re-dump on a schedule — or use `--postgres DSN` if you have PostgreSQL.

assistant: The practical benefits of using PostgreSQL with graphify instead of SQLite depend on what you're optimizing for. Here's the honest breakdown:

## Benefits of PostgreSQL + graphify

### 1. Native live schema introspection

graphify has `graphify --postgres "postgresql://..." .` which reads the catalog directly. No dump step, no reformatting, no cron to keep `.sql` snapshots fresh.

### 2. Always-current graph

The graph reflects the live schema at extraction time. With SQLite you're stuck with point-in-time dumps that go stale.

### 3. More complete relationship extraction

The PostgreSQL introspector queries:
- `information_schema.tables`
- `information_schema.views`
- `information_schema.routines` (functions/procedures)
- `pg_constraint` for foreign keys (including composite FKs)

It reconstructs proper `ALTER TABLE ... ADD CONSTRAINT ... FOREIGN KEY` DDL, which `tree-sitter-sql` parses cleanly. SQLite dumps often need manual compacting to parse well.

### 4. Richer routine/function graph

PostgreSQL exposes stored function/procedure bodies. graphify can parse them and extract `reads_from` / `references` edges from SQL inside the routines.

### 5. One command, no intermediate files

```bash
graphify --postgres "postgresql://user:***@localhost/dbname" .
```

vs. the SQLite pipeline:

```bash
sqlite3 db.sqlite .schema > db.sql
# reformat multiline DDL
graphify schema-dir --no-gitignore
```

### 6. Better fit for multi-user / production schema

If multiple tools or people mutate schema, Postgres's catalog is the single source of truth. SQLite schema is file-bound and harder to share safely.

## What it does NOT fix

- graphify still only indexes **schema/metadata**, not row data.
- It still doesn't read actual table contents, PII, or query result sets.
- Community labeling still needs `openai` extra.

## The main cost / tradeoffs

| Cost | Detail |
|---|---|
| Operational overhead | Running a Postgres server vs. file-based SQLite |
| Migration work | Converting SQLite schemas, data, and application code |
| Environment complexity | Backups, users, permissions, connection strings |
| Not free | For this workspace, SQLite is already embedded everywhere |

## When it makes sense for you

Switching to PostgreSQL *just* for graphify is probably not worth it. It only makes sense if you're also hitting other Postgres wins:

- Concurrent writers
- Larger datasets
- Need for stored procedures / triggers / advanced indexing
- Multi-user access patterns
- Existing Postgres infrastructure

## Recommendation for this workspace

Stay with SQLite for now. The dump-to-`.sql` pipeline works. Better investment: automate the dump + compact + graphify refresh for your SQLite files, and keep Postgres in mind if you ever outgrow SQLite for real operational reasons.
