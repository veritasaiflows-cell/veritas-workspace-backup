### memory_search timeout - diagnosed, provider is healthy

The session-start failure (`memory_search timed out after 15s`, `disabled: true`) was **not** an
embedding provider fault. Two compounding causes:

- **Cold embedding load.** A cold `nomic-embed-text` load measured 4,055-7,295 ms, and Ollama
  unloads the model after roughly 5 minutes idle. The first search of any session paid that
  against a 15s tool deadline.
- **Budgets are advisory, not enforced.** `runMemorySearchOptionalPhase`
  (`dist\tools-C_UMYlhe.js:366-394`) races the phase against a `setTimeout` but never cancels the
  underlying work - there is no `AbortController`, unlike `runMemorySearchToolWithDeadline`
  (line 328) which does abort properly. Proof: the wiki phase reported "timed out after 5s" while
  its own `elapsed_ms` was 17,151.

Measured: `corpus=all` `toolMs=25154`; `corpus=memory` 5,145 ms and safe. The declared budgets
(5s memory init + 8s memory phase + 5s wiki supplement + overhead) are structurally over a 15s
deadline even when healthy. The sessions corpus is hardcoded off at line 757. The index has grown
to 9,884 chunks from the 8,724 the 08-20 hotfix was tuned against.

**Durable behavioral consequence:** prefer `corpus=memory` for routine recall. Use `corpus=all`
only when wiki content is genuinely required, and expect it may exceed the deadline.

The budget-enforcement defect itself was **not** fixed. Fixing it means editing compiled JS and
deepening fork debt for a path that has a safe workaround.

### `no such table: memory_index_chunks_vec` - diagnosed, no data lost, detector added

`openclaw memory status --index` emitted `Memory index failed: no such table:
memory_index_chunks_vec` earlier today. It is transient and self-healing, and it did not damage
anything: all nine agent stores currently hold the table and every one has `vector_rows == chunks`
(main 9891/9891). Two clean reruns of `openclaw memory status --index` reproduced no error, so it
is a race, not a deterministic missing table.

The vec table is not part of the base memory schema. It is created lazily by `ensureVectorTable()`
in `manager-Bdg_bLtw.js:1599`, which does a bare `DROP TABLE IF EXISTS` followed by
`CREATE VIRTUAL TABLE ... USING vec0(...)` with no surrounding transaction and no cross-process
lock. `replaceMemoryVectorRow` (`:3031`) swallows a failed `DELETE` but lets the `INSERT` throw, so
a writer that lands inside that drop/create window fails with exactly this message. The CLI
`--index` path is a *second* writer against the same agent SQLite file while the gateway's file
watcher is indexing; the `openclaw-agent.sqlite.reindex-lock.sqlite` lock only covers full
reindexes, not incremental ones.

Second, latent and worse: `replaceVirtualTable` (`:659`) in the full-reindex publish path. When the
shadow database has no `memory_index_chunks_vec` - which is what happens if sqlite-vec failed to
load during the shadow build, and `vec0.dll` has been observed locked on this machine - `createSql`
is null, so it drops the live table and returns *without recreating it*. Meta still reports
`vectorDims: 768`, semantic recall silently degrades to keyword-only, and nothing errors at query
time.

Fix taken: detection, not another compiled-JS patch. `semantic_memory_maintenance.py` gained
`vector_store_integrity_state()`, a read-only sweep of every `~/.openclaw/agents/*/agent/
openclaw-agent.sqlite` that flags a missing vec table or any `vector_rows != chunks` drift. It
reads the plain `memory_index_chunks_vec_rowids` shadow table, so it needs no sqlite-vec extension.
It rides the existing 4x/day maintenance cron - no new job, no schedule change. Verified against a
synthetic fixture: catches a dropped table and partial vectors, stays quiet on healthy and on an
empty index.

Operating rule that follows: do not run `openclaw memory status --index` while the gateway is live.
Plain `openclaw memory status` is read-only and safe; indexing belongs to the gateway watcher and
the maintenance cron.

### Lessons

- A new cron job is not governed until it appears in the operator ledger. `cron_freshness_spine.py`
  reads `ledger_jobs` from `tmp/cron-operator-ledger.json`, so regenerating the control packet
  alone will not surface an unregistered job - run `cron_operator_ledger.py --write --write-md
  --validate` to expose it, then write the contract.
- A declared timeout constant proves intent, not enforcement. Verify there is a real cancellation
  path (`AbortController` or equivalent) before trusting a budget; a `Promise.race` against
  uncancelled work lets the "timed out" branch report a number smaller than its own elapsed time.
- `--command-argv` through PowerShell needs escaped inner quotes
  (`'[\"python\",\"script.py\"]'`); native-command argument passing strips unescaped ones.
