## Executive Answer

PM jobs should not all be executed daily.

PM visibility should be refreshed daily, preferably twice daily on normal operating days and after material workflow changes. The current system mostly does that. The PM job queue is refreshed through `pm_control_packet.py`, and cron currently keeps the main PM control packet fresh enough for routing. The right cadence is:

- Refresh PM control and PM queue state daily.
- Run PM execution-loop dry-run daily or during greenkeeper review.
- Execute at most one proof-safe PM job per collision group only when stale, ready, and useful.
- Do not rerun every PM job daily; that would duplicate work, burn validation budget, and create churn without better truth.

Current state is good but not clean:

- `tmp/pm-control-packet.json` is current and valid.
- PM control sub-signals are fresh.
- Cron contract drift is zero.
- Cron freshness has no stale jobs and no missing expected artifact contracts.
- There are still 3 blocked cron signals and 1 stale required PM cockpit source.
- The live PM continuation dispatcher payload still references older PM sidecars as first-read surfaces instead of making `tmp/pm-control-packet.json` the explicit primary route.

## Definitions

This audit separates three different things:

1. PM control refresh
   - Rebuilds the PM truth surface: `tmp/pm-control-packet.json`.
   - Recomputes readiness, stale lanes, implementation jobs, handoff, heartbeat candidates, and source health.
   - Safe to run frequently because it is review-only.

2. PM job queue refresh
   - Happens as part of `pm_control_packet.py`.
   - Produces the current implementation queue and stale-lane digest.
   - It is not the same thing as executing jobs.

3. PM job proof execution
   - Runs selected proof commands for a job through `pm_execution_loop.py`.
   - Should be bounded, collision-aware, and stale/event-driven.
   - Should not run all jobs daily.

## Duplication Risk

The system already has several anti-duplication controls:

- `pm_execution_loop.py` runs dry-run by default.
- It selects one job, not all jobs.
- It enforces collision groups.
- It uses validation budgets.
- It skips jobs completed by ledger.
- PM control distinguishes finance-domain repair debt from implementation blockers.
- PM control reports `auto_cron_executable_job_count=0`, meaning cron is not currently allowed to execute arbitrary PM jobs.

Remaining duplication risks:

1. Old sidecars versus PM control packet
   - The live PM dispatcher still names old sidecars first.
   - This can cause main-session pickup to inspect multiple surfaces for the same decision.

2. Re-running PM control after every sub-action
   - Some closeout paths regenerate PM control repeatedly, which is useful after material changes but wasteful if done as ritual.

3. Treating domain debt as implementation jobs
   - PM currently prevents this correctly: finance repair conveyor rows are classified as finance-domain debt, not implementation blockers.

Recommendation:

- Keep PM control as the canonical PM truth surface.
- Retire or demote compatibility sidecars from first-read dispatcher payloads.
- Refresh PM control after material actions, not after every no-op.
- Keep PM execution event-driven and ledger-aware.

## Recommended Cadence

### Baseline Daily Cadence

Keep:

- PM control refresh twice daily through `PM - Main Session Continuation Dispatcher` at 07:20 and 14:20 Phoenix time.
- Cron control digest refresh at morning/post-close windows.
- Weekly OS improvement radar on Sunday.

Add or formalize:

- Daily PM source-health check: require `pm_cockpit_source_health.stale_required_count=0` or explicitly accepted known-monitor exception.
- Daily PM execution-loop dry-run after PM control refresh:

```powershell
python scripts\pm_control_packet.py --write --write-db --validate
python scripts\pm_execution_loop.py --write --validate
```

Do not run `pm_execution_loop.py --execute` on a schedule until the selected job is proof-safe, collision-distinct, and explicitly intended for automated pickup.

### Event-Driven Refresh

Refresh PM control immediately after:

- A workflow closeout changes PM state.
- A helper lane completes material work.
- Cron blockers are repaired.
- SQL/JSON migration state changes.
- PM cockpit source registry changes.
- A PM job proof executes.

Use:

```powershell
python scripts\pm_control_packet.py --write --write-db --validate
python scripts\cron_control_packet.py --write --validate
```

### Weekly Maintenance

Keep weekly radar proof, but use it for:

- Operating hygiene.
- Stale source classification.
- Validator timing drift.
- Worktree/checkpoint review.
- PM/cron contract consistency.

Do not use weekly radar as a substitute for daily PM control refresh.

## Performance And Efficiency Recommendation

Best cadence now:

1. Twice daily PM control refresh.
2. Twice daily cron control/freshness digest.
3. Daily PM execution-loop dry-run.
4. Event-driven PM refresh after material workflow changes.
5. Weekly OS radar for lower-frequency hygiene.
6. No daily execution of all PM jobs.

This gives enough freshness without duplicating proof work.

## Final Finding

PM job visibility should be daily-current. PM job execution should be selective.

The current system has the right architecture: PM control is refreshed by cron, PM execution is dry-run by default, and stale/completed jobs are skipped. The improvements needed are not "more daily jobs." The improvements are tighter route clarity, one stale PM source repair, and explicit cadence health so we avoid both duplicated work and stale decisions.
