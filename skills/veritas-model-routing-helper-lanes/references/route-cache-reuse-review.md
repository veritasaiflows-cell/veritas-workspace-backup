# Route Cache Reuse Review

Read when a route's prompt-cache reuse is in question, when cache behavior differs between routes serving the same model, or before proposing a cache-sensitive route change. This is descriptive route diagnosis; every config, routing or parameter change it recommends is owner-gated.

1. **Establish whether the route can cache at all before interpreting any hit rate.** OpenClaw cache control is family-gated: `resolveCacheRetention` returns a value only for an Anthropic-family route (`anthropic`, `anthropic-vertex`, Claude on `amazon-bedrock`, or `modelApi: "anthropic-messages"` with an explicit cache setting), a Google generative route (`gemini-2.5*` or `gemini-3*`), an OpenAI-family responses/completions route, a `bedrock-converse-stream` route, or a route declaring `compat.supportsPromptCacheKey: true` or `compat.cacheControlFormat: "anthropic"`. A provider on a native non-OpenAI API matches none of these - verified case: `api: "ollama"` served over `/api/chat` - so a global `agents.defaults.params.cacheRetention` is silently inert there. **Done:** an explicit per-route eligible/inert verdict from the route's `api` and `compat`; never assume a global cache setting covers a route.

2. **Compare the same model across routes before attributing a deficit to the model.** Read per-call counters read-only from the main agent trajectory store (`trajectory_runtime_events`, `model.completed` events, `data.promptCache.lastCallUsage.{cacheRead,input}`) and aggregate hit% = cacheRead/(cacheRead+input) per route. The same model on two routes isolates the transport as the variable. Verified: GLM-5.3 87.7% direct vs 45.9% via Ollama Cloud; GLM-5.3-flash 92.7% vs 21.9%; Kimi K3 83.8% vs 9.2%. **Done:** a per-route hit-rate table for one model, with the sample size per route.

3. **Separate a missing counter from a miss.** A route whose events carry `promptCache: null` or no `cacheRead` key is an instrumentation gap, not provider failure; reuse is only readable from the build that first maps the provider's cached-token counter into `cacheRead`. Name the readable window and exclude earlier calls from any rate. When one route oscillates between near-zero and high reuse while everything else is stable, report it as unresolved provider-side behavior rather than naming a cause. Missing-versus-zero accounting semantics remain owned by [Accepted-Outcome Efficiency Review](efficiency-evaluation.md). **Done:** readable window named, unreadable calls excluded, unexplained variance left unresolved.

4. **For an inert-cache route, check the two multipliers before proposing any fix.** Fallback order - a configured fallback chain can place a worse-reusing route ahead of a better-reusing route for the *same* model. Context window - a very large cap on a route that does not reliably reuse prefixes means every miss re-prefills the full window; treat a cap as a miss-cost bound and never as a hit-rate fix, because it does nothing to an oscillating reuse rate. On `api: "ollama"` the two context knobs are independent: `params.num_ctx` is forwarded as the native `/api/chat` `options.num_ctx` (a server-side limit), while automatic compaction gates on `model.contextWindow` - so lowering `num_ctx` alone leaves the client gate above the server cap, and prompts between the two values are rejected with no compaction trigger. Move `num_ctx` and `contextWindow` together, and size any proposed cap first by counting the calls and sessions whose prompt exceeds it from the same `model.completed` store as step 2: the affected set is often far smaller than the change appears to cover. **Done:** each multiplier named with its current configured value; any proposed cap carries its paired `contextWindow` value and the affected model entries, or is reported as unsafe.

5. **Do not probe a provider whose credential lives only inside the Gateway.** When the provider block carries `auth: "api-key"` and no `apiKey` field, the credential resolves from the protected store at runtime; an external request to the provider endpoint returns an authorization error and proves nothing about provider behavior. Confirm through a Gateway-run session on that route instead. **Done:** the probe venue stated, or the limitation reported instead of an inferred provider verdict.

6. **Close with a ranked routing recommendation and its authority.** Rank the routes that reuse cache better for the same model, and mark every fallback-order, parameter or config change as owner-gated. **Done:** recommendation plus an explicit statement that no route or config change was applied.
