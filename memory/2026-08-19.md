### 2. `scripts/wf84_sqlite_mutex.py` — stale-lock reclamation added
Root cause of the `wf84_canonical_finance_data_plane` crash and the same class as the 2026-08-19 dead-PID lock above: a 180s timeout with no liveness check, so one killed writer wedged every later run. Added `pid_alive()` (Win32 `OpenProcess`/`GetExitCodeProcess`; **never `os.kill(pid,0)` on Windows** because CPython routes non-console signals to `TerminateProcess`), `classify_lock()`, atomic `os.rename` reclaim so only one racer wins, append-only audit at `tmp/wf84-sqlite-mutex-reclaims.jsonl`, and a release guard that only unlinks the lock if still ours. Verified: dead holder reclaimed in 0.007s (was 180s timeout); **live holder correctly NOT stolen** (times out as designed).

### 3. `scripts/finance_ticker_card_refresh_gate.py` — masking defect fixed (the actual answer to Randall's challenge)

### 4. Tier-count divergence — my original premise was wrong; found a different real defect
`tier_routing_state.auto_tier` vs `universe_membership.tier` divergence is **by design**: `universe_membership.tier` comes from the static registry `data/finance/universe-v1.json`, while `auto_tier` is the dynamic WF78 computed tier from `tmp/wf78-auto-tier-routing.json`. Not a bug.
The real defect: `tier_routing_state` is a **mirror** that only refreshes on a full `finance_sql_canon` rebuild, and it was serving a 12:45Z generation while the artifact was 21:40Z — a 9h lag. It already stored `source_artifact_sha256` / `source_generated_at_utc`, but **nothing ever compared them.** Added report-only check `tier_routing_state_mirrors_current_router_artifact` to `finance_sql_canon_access.py`, then reconciled via the purpose-built `sql_canon_tier_routing_refresh.py --write --apply-db --validate` (backup + rollback + `reference_levels_preserved=true`, derived non-capital routing only). ### Severity-model fix (near-miss worth remembering)
My new mirror check initially returned `ok=False`, which made the guard `status=blocked`. `_guard()` **raises**, so every `ticker_state()` call would have thrown, and `chain_manifest.py:255` marks this script `recovery_posture: fail_chain`. A 9-hour derived-mirror lag would have become a full finance-answer outage. Added `severity="warning"` routing to `_validation_payload` so freshness-lag findings degrade confidence instead of failing the read path closed. **Durable lesson: before making a new check fail closed, check whether its consumer raises and whether the chain treats it as `fail_chain`.**

### Ordering lesson (extends item 3 of the WF74 lane above)
Any WF78 router regeneration silently invalidates **two** downstream mirrors, and nothing enforces the rebuild order: (a) SQL-canon `tier_routing_state`, (b) the derived `tmp/canonical-finance-data-plane.sqlite`. Observed live: re-running `wf78_intelligence_routing_v2.py` immediately re-broke both `tier_routing_state_mirrors_current_router_artifact` and `router_core_fields_match_wf84`. Correct order after any WF78 run: `sql_canon_tier_routing_refresh.py --write --apply-db` -> `canonical_finance_data_plane.py --write --write-db` -> `canonical_finance_data_plane_phase6_10.py`. Also note `canonical_finance_data_plane.py --write` alone does NOT rebuild the SQLite companion; `--write-db` is required (bare `--write` returns `"sqlite": null`).
