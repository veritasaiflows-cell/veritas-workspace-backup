## How the Wiki Synthesis Layer Works

### What it is

The wiki is a set of **8 durable Markdown pages** inside `wiki/` that act as a "second brain" — a human-readable map of what the workspace knows, what it's working on, and where things should route. It is **not** canon, approval, or execution authority. It's a map, not a decision-maker.

### The 8 pages

| Page | What it does |
|---|---|
| `wiki/README.md` | Front page — status, boundary, action posture, source artifact |
| `wiki/index.md` | Table of contents + current summary numbers |
| `wiki/os2/OTEL To Proposal Route.md` | Maps operational telemetry → learning metadata → improvement opportunities → proposals → WF88 control → wiki → startup/status |

| `wiki/source-map/WF88 Wiki Source Map.md` | Exact source artifacts each page draws from |

### What "6 self-prompts" means

These are **not** prompts the wiki sends to a model. They are 6 standing questions embedded in the RSI Control Loop page that a new session (or cron run) should ask itself when reviewing state:

1. What changed in the evidence, and which exact artifact proves it?
2. Is this a one-time note, a wiki update, a WF74 proposal, a PM lane, a skill proposal, or a validator gap?
3. What action should surface next, and which stop line prevents overreach?
4. Did an improvement recommendation route to a docket, PM job, owner packet, or monitor-only state?
5. Does any wording imply canon/approval/execution authority the source artifacts don't grant?
6. What should a new session open first before repeating this decision?

Think of them as a checklist that forces evidence-based routing instead of vague "improve things" drift.

### What "leak guard clean" means

The wiki synthesis packet checks two things before writing:
- **Open unrouted recommendations: 0** — every recommendation the system generated has been routed to a concrete destination (WF74 docket, PM job, owner packet, monitor-only state, etc.). None are floating loose.
- **Auto-apply count: 0** — no recommendation was automatically applied. Everything stops at routing/proposal unless a human approves.

If either of those numbers were nonzero, the wiki would report a leak and block front-door "healthy" claims.

### Why this design works

**Before this layer:** Recommendations, improvements, and learning signals were scattered across `tmp/` artifacts. A new session had to know which files to open and what they meant. Improvements could sit as chat residue and get lost.

**After this layer:** Every night at 10:12 PM, the workspace refreshes all its proof surfaces, routes every open improvement to a concrete destination, regenerates the wiki pages, and updates the front doors (startup brief, status card, future-session packet). When a new session opens — whether after compaction, a fresh day, or a context loss — it sees the wiki index first, gets the current action posture, and knows exactly which artifacts to drill into. Nothing is hidden, nothing auto-applies, and nothing claims to be healthy while unrouted recommendations or nonzero auto-apply exist.

The cron contract file (`state/cron-contracts/runtime-wf88-wiki-synthesis-refresh.json`) explicitly blocks:

- Capital deployment or paper/live execution
- Brokerage/account action or money movement
- Customer/external output
- Model training claims
- Owner approval inference

If any of those flags flip, the contract validator catches it before the front doors can report healthy.

### Bottom line

## What to do about it

### The high-leverage fix: changed-input prefilters

The pattern is mechanical and repeatable. For each of these 15 jobs:

1. **Before** spawning the model call, compute a hash of the input artifacts the job reads
2. **Compare** against the hash from the last successful run
3. **If unchanged:** skip the model call entirely, write a `skipped_unchanged` proof artifact, exit 0
4. **If changed:** proceed with the model call as normal

This is not prompt compression. It's not changing the model. It's a deterministic gate that says "nothing changed, don't burn 50K tokens to get the same answer."

**Estimated impact:** For jobs with 90%+ cache ratios, the inputs are almost never changing between runs. A changed-input prefilter would skip 80-95% of these model calls. At ~50K tokens per call across 15 jobs running daily, that's roughly **500K-700K tokens saved per day** — or about $0.15-0.25/day in direct cost, plus the latency and attention savings.

### What NOT to do

- **Don't compress prompts blindly.** The scorecard flags 11 prompt-compression candidates, but compression risks changing model behavior. Changed-input prefilters are safer — they skip the call entirely when nothing changed, with zero risk of degraded output.
- **Don't reduce cron cadence without proof.** Several jobs are flagged as `cadence_or_skip_when_unchanged_review`, but changing schedules requires separate approval and regression proof. The prefilter approach achieves the same savings without touching schedules.
- **Don't delete validators.** The 89-command bundle is large but correct for broad closeout. The fix is routing to the right budget, not removing validators.
