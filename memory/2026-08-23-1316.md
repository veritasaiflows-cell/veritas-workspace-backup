assistant: A turn circuit breaker would be a **between-tool-call state machine**. It would not kill a running command. It would stop the agent from starting more work once the turn becomes too large.

### Proposed lifecycle

`OPEN → WARNING → TRIPPED → CHECKPOINTED → NEW TURN → RESUMED`

1. **OPEN:** Work proceeds normally.
2. **WARNING:** At roughly 75% of budget, broad searches and large reads stop.
3. **TRIPPED:** No additional research tools may start.
4. **CHECKPOINTED:** Current findings and exact next action are saved.
5. **NEW TURN:** A fresh turn loads only that bounded checkpoint.
6. **RESUMED:** Work continues without replaying the entire transcript.

### Proposed limits

Trip when the first threshold is reached:

- 20 tool calls;
- three minutes of turn work;
- 30,000 estimated context tokens;
- 120 KB of cumulative tool output;
- a pending operation expected to generate an unusually large response.

A warning could occur at 15 calls, two minutes, 22,500 tokens, or 90 KB.

### What the checkpoint contains

A small JSON artifact would record:

- task and lane IDs;
- objective and authority boundary;
- completed phases;
- source paths and hashes;
- extracted facts and citations;
- current report path and hash;
- last successful tool;
- unresolved questions;
- exact next command;
- validation status;
- retry count and stop lines.

The checkpoint—not the entire conversation—becomes the next turn’s input.

## How it will work

```text
turn/start
   ↓
Create trusted per-turn counter
   ↓
Intercept every tool request + observe token usage
   ↓
24 calls / 48k tokens → warning and graceful-close mode
   ↓
30 calls / 60k tokens → block new work, checkpoint, interrupt
   ↓
turn/completed(interrupted)
   ↓
Resume from checkpoint in fresh turn/thread
```

The exact behavior:

- Tool calls 1–30 are allowed.
- When call 30 is reserved, the turn enters “draining” mode:
  - already-running tools may finish;
  - call 31 is rejected before execution;
  - duplicate callbacks are deduplicated by tool-call ID.
- `thread/tokenUsage/updated.tokenUsage.last.inputTokens` supplies the latest actual context occupancy. We must use raw input tokens, including cached input—not cumulative session usage.
- At 24 calls or 48,000 tokens, the runtime tells the agent to stop expanding scope and prepare a bounded handoff.
- At 30 calls or an observed 60,000 tokens, the runtime:
  1. Blocks new tool dispatch.
  2. Writes the checkpoint outside the model/tool loop.
  3. Calls app-server `turn/interrupt`.
  4. Waits for `turn/completed` with status `interrupted`.
  5. Returns a controlled “checkpointed” outcome rather than an idle-timeout error.
- The gateway does not restart when this happens.

A token-triggered continuation cannot merely create another turn on the same Codex thread—the old context would still be present. It must either compact the native thread or, preferably, rotate to a fresh Codex thread and bootstrap it from the checkpoint. A tool-count-only trip can reuse the same thread if context is still comfortably below the warning threshold.

## Gaps to close

1. **The warning has no delivery mechanism.** At 24 calls / 48k, "the runtime tells the agent to stop expanding scope" — but there is no injection seam between inferences. The only realistic channel is wrapping advisory text into tool results on the dynamic path (and deny-message text on `PreToolUse`). If the model ignores it, the hard trip catches it. That's acceptable, but the plan should say so explicitly instead of implying reliable graceful-close.

2. **Verify `tokenUsage.last` semantics before building anything.** One schema-check spike (`thread/tokenUsage/updated` against the generated TS types): is `last` per-request or thread-cumulative, does it include cached input, and how often does it fire? If it's cumulative or sparse, the 48k/60k thresholds are miscalibrated from day one. This is a 30-minute task that de-risks the whole token path.

3. **Checkpoint content is undefined.** A checkpoint for fresh-thread bootstrap cannot be the raw context — it must be a structured handoff: task objective, completed phases, file deltas, open decisions, counters, trip reason. Also: in-flight tools may still be writing files while the checkpoint snapshots state, so the checkpoint must record in-flight tool identities and mark affected surfaces dirty/pending. Without this, "resume from checkpoint" resumes garbage.

4. **Concurrency scope.** Counters are per-turn, but one gateway runs many sessions/threads. The state store needs per-thread keys, cross-session safety, and a job identity that survives thread rotation so the auto-resume cap actually binds. Suggest cap = 3 continuations per job, then stop and surface to you.

5. **Missing-telemetry fallback rule.** "Never interpret missing as zero" is right but incomplete: if no fresh usage sample exists near the trip decision, the continuation choice is undecidable. Rule should be: stale/missing telemetry → take the conservative path (fresh thread, don't reuse).

6. **Kill switch.** Add a config-level disable flag so the breaker can be turned off without a plugin rebuild. First deployment of an enforcement layer that interrupts turns will have false positives; you need an instant off.

7. **Test list additions:** out-of-order/duplicate tokenUsage updates, concurrent turns in two sessions, kill-switch behavior, watchdog interaction during interrupt (must clear the 240s guard), and rollback of the plugin build itself. Keep the cooperative Python guard running as fallback during shadow.
