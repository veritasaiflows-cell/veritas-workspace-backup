## Verdict

The cron fleet is **broad and mostly healthy at the artifact layer, but the monitoring is reporting green while a daily finance job has failed four runs straight.** The single most important finding: the **WF78 Daily Freshness and Promotion Proof** cron — the job that refreshes ticker freshness and feeds WF84/WF85 — has failed its last 4 consecutive weekday runs at the agent-execution layer, yet `escalation_signal_count = 0`. The escalation pipeline does not observe gateway job execution state, so job-level failures are invisible to the "all green" rollup. This is the likely root cause of the stale-freshness problem flagged in the finance audit (only 27/200 tickers truly fresh).

Everything else is secondary: cron clutter (25 disabled/expired jobs + 9 store backups), a model-posture change (gpt-5.4-mini promotion) that correlates with the failures, and 5 new unverified jobs that first fire Monday.

## HIGH severity

### H1 — WF78 Daily Freshness cron: 4 consecutive failures, invisible to escalation

- **Job:** `Finance - WF78 Daily Freshness and Promotion Proof` (id `93de5b09-…`), schedule `8 6 * * 1-5` (weekdays 06:08 Phoenix), isolated agentTurn, model `openai/gpt-5.4-mini`, `timeoutSeconds: 900`.
- **State:** `lastStatus = error`, `consecutiveErrors = 4`.
- **Run history (last 10):** the most recent 4 finished runs all `status: error`; error string is the wrapped command failing at the tool/agent layer (`"…wf78_daily_freshness_cron_runner.py --write --validate" (agent) failed`), and one run `"Agent couldn't generate a response."` Durations ranged 95s–597s against the 900s cap; agent output_tokens were near-empty (6–273). The last clean cron run was 2026-06-08 (`status: ok`, though completion decision was `BLOCKED`).
- **Critical detail:** the underlying script is **not** broken. Manual run on 2026-06-14 17:11 returned `status: ok` with all 11 chained steps passing (`wf78_daily_freshness_loop`, `intraday_quote_snapshot_proof`, `finance_decision_factory`, `trade_grade_os_freshness_cron_runner`, `cron_operator_ledger`, `cron_freshness_spine`, `cron_signal_scorecard`, `escalation_trigger`, `cron_control_packet`, etc.). The failure is at the **cron agent-execution layer**, not the Python.
- **Probable contributors:** (a) the runner is a long subprocess chain (8–10 min) that, with agent overhead, flirts with the 900s timeout; (b) the job model was recently changed to `gpt-5.4-mini`, a lighter model that appears to be failing to drive/complete the long wrapped command (very low output token counts). gpt-5.4 runs of the same job also errored recently, so model is a contributor, not the sole cause.
- **Impact:** This is the chain that refreshes ticker price/band/stop freshness and promotion proof. Its silent failure is the most credible explanation for the finance audit's "only 27/200 truly fresh, quotes 2 sessions stale" finding. The proof artifacts (`cron-control-packet.json`, `escalation-trigger.json`) still look fresh and green **because they are regenerated by manual/heartbeat runs of the same script** — masking the cron failure. Circular monitoring.

### H2 — Escalation pipeline is blind to job execution failures

- `escalation_trigger.py` derives `escalation_signal_count` from `cron-signal-scorecard.json` and `cron-freshness-spine.json` only (freshness/signal artifacts). It does **not** read gateway job `state.consecutiveErrors` / `lastStatus`.
- Consequence: a daily enabled job can fail 4× in a row (H1) while `escalation_signal_count = 0` and `should_wake_main_session = false`. The "green" cron rollup is structurally incapable of seeing execution failures.
- The cron jobs also carry **no `failureAlert`** configuration, so the gateway itself sends no failure notification either. Failures are silent on both paths.

## Recommendations (priority order)

1. **Fix WF78 daily freshness cron (H1).** Two levers, both reversible:
   - Raise `timeoutSeconds` (e.g. 900 → 1500) so the long chain has headroom, and/or move this heavy runner off `gpt-5.4-mini` back to `gpt-5.4`.
   - Better still: have the cron message invoke the deterministic runner with **minimal agent reasoning** (the script already self-validates; the agent only needs to launch it and read one JSON), reducing agent-layer fragility. Then run the job once manually via `cron run` to confirm a clean cron-path execution before trusting Monday.
2. **Close the escalation blind spot (H2).** Extend `escalation_trigger.py` (or `cron_control_packet.py`) to read gateway job `state.consecutiveErrors`/`lastStatus` and raise an escalation signal when any **enabled** job has ≥2 consecutive errors. Add `failureAlert` to the handful of mission-critical finance jobs so the gateway notifies on failure independently of the artifact pipeline. This is the structural fix — without it, the next silent failure repeats.
3. **Stabilize M1 jobs.** Replace the inline Python heredoc in the Post-Close Review Refresh job with a committed script; re-check the Tier A Late-Session probe's send step.
4. **Re-anchor model posture (M2).** Decide a rule: heavy long-chain runners ≥ gpt-5.4; reserve gpt-5.4-mini for short, single-artifact proof jobs. Update TOOLS.md if the posture has intentionally changed.
5. **Prune clutter (M3) — approval-gated.** After one fresh store backup: remove expired one-shots and the retired `Main Session … Handoff` generation, and archive the old `jobs.json.bak*` files. Config-adjacent, so explicit go-ahead first.
6. **Verify the 5 new jobs Monday (L1).** Confirm first weekday runs succeed; don't assume.
