user: what do we use frozen hashes for?
assistant: Frozen hashes prove that the files reviewed are exactly the files Main intended to hand off.

For each handoff file, we record:

- Path
- Byte size
- SHA-256 hash
- Snapshot/attempt identity

The QA agent recomputes those hashes before reviewing. This gives us four protections:

1. Moving-target protection  
   If Main or another lane edits a file after the handoff, the hash changes and QA must stop or receive a new snapshot.

2. Version certainty  
   When QA says “PASS,” we know precisely which version passed—not merely a filename that may have changed.

3. Context integrity  
   It prevents an agent from accidentally reviewing stale, substituted, missing, or partially copied files.

4. Efficient repair handoffs  
   After a failure, we can send only changed-file deltas instead of replaying the entire context package.

In the P0 work, independent QA verified that all six frozen files matched their recorded byte sizes and SHA-256 hashes before checking the live cron and OTEL state.

Important limitation: a matching hash proves identity and integrity, not correctness. Tests, live canaries, contract validation, and independent judgment still establish whether the frozen code is actually good.

Think of it as: “This is unquestionably the exact code QA reviewed,” not “this code is automatically correct.” Source: `memory/2026-06-03.md#L16`

## Best model-run enhancement

Use a two-layer design:

```text
Deterministic AST graph
        ↓
exact code structure and call relationships
        +
Model-generated semantic overlay
        ↓
purpose, ownership, workflow stages, risks and operating relationships
```

Do not replace AST extraction with model runs. AST is faster, cheaper, and more reliable for functions, imports, definitions, and calls. Model runs should add the relationships code cannot express reliably.

### 1. Incremental model extraction

Before dispatching a model, calculate frozen hashes for every source file:

- unchanged file + unchanged extraction prompt → reuse cached graph fragment
- changed file → run semantic extraction
- deleted file → remove its fragment
- changed extraction specification → deliberately regenerate affected fragments

The skills graph currently has zero changed source hashes, so a full 51-file model rerun would be wasted tokens.

### 2. Targeted semantic overlays

Use isolated model runs for high-value surfaces only:

- new pre-dispatch gates
- cron control and payload ownership
- OTEL control and privacy boundaries
- validation and QA relationships
- workflow promotion and memory paths
- important entry points and generated artifacts

For scripts, I would start with roughly 20–40 control-plane files, not all 1,797 files.

Each model should emit constrained JSON containing:

- source and destination concepts
- directed relationship
- exact source span
- confidence
- `EXTRACTED`, `INFERRED`, or `AMBIGUOUS`
- source SHA-256
- extraction-spec hash
- model, session, attempt, and token attribution

### 3. Model-run cleanup of the skills graph

A bounded model pass can improve the existing graph without rebuilding it:

- name the 25 generic `Community 0`, `Community 1`, etc. clusters
- reassess the 48 inferred edges, whose average confidence is only 0.50
- construct explicit workflow paths
- merge aliases and duplicate concepts
- run adversarial questions and identify missing relationships
- reject conclusions that lack an exact supporting source span

### 4. Independent model QA

Use a second clean model run to challenge the extracted overlay:

- Is every relationship supported?
- Is its direction correct?
- Did extraction cross an authority boundary?
- Are important nodes missing?
- Can representative questions retrieve a concise path?
- Did the model invent relationships from general knowledge?

Only validated overlays should be promoted into the queryable graph.

## Model runs versus backend API calls

Model runs offer:

- no additional API-key or backend integration requirement
- access to workspace doctrine and operating context
- stronger reasoning about ownership, purpose, authority, and workflow meaning
- bounded parallel chunk processing
- easy use of separate extraction and QA roles

The tradeoffs are:

- lower throughput than a batch API
- more variable latency and formatting
- potential context contamination unless runs are isolated
- harder accounting unless token attribution is explicitly captured

Backend APIs remain better for massive standardized extraction. For this workspace, however, hash-gated model runs are the better near-term choice because the valuable work is targeted semantic reasoning—not bulk parsing.
