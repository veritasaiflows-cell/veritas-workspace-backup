## Decision

**Strengthen and prove the existing harness before adding capabilities.** We have substantial governance, memory, delegation, task-state, and evaluation infrastructure. We do not currently have fresh, sufficient evidence that WF88/OTEL continuously turn observations into accepted changes and later measurable improvement.

Preparation for more capable models means better evaluation, recoverability, containment, provenance, and human control. It does not establish AGI/ASI, predict its arrival, authorize model training, or justify expanding autonomy.

**Recommended first slice:** Phase 0 recovery acceptance and evidence refresh. Then one production-relevant, end-to-end improvement example. Do not restart the retired WAVE2 ten-job cohort or build another agent/memory runtime.

## Phased execution plan

Effort below is a planning estimate in focused implementation slices, not a calendar promise. Re-scope after Phase 0. Each slice has one owner, exact writes, independent review where warranted, and Main acceptance.

### Phase 0 — Prove recovery and establish fresh truth (P0; about 1 slice)

1. Reconcile the existing Python-path repair with current automation payloads and any other active repair lane. Do not rewrite already-correct jobs.
2. Obtain post-update execution evidence in the actual scheduler environment for WF88 and OTEL. Validate the weekly radar's interpreter path and attribution step separately. A manual script success is insufficient scheduler proof.
3. Refresh only the required upstream/downstream proof chain, including RSI, attribution, OTEL, WF88, and harness status; preserve pre-refresh evidence. Prove freshness, source identity, privacy, and validation together.
4. Reconcile WF88's obsolete WAVE2/paper-control routing with current owners; preserve the retired cohort and deny-only execution boundaries.
5. Prepare a bounded failure-delivery repair if still needed. Do not send a test to Telegram or change routing without the exact approval.

**Exit:** fresh source-derived packets plus verified execution receipts, or an explicit remaining blocker; no stale green reused as recovery proof. Existing failure route is either proven or visibly marked unverified. Payload/service/delivery changes and any forced external delivery remain owner-gated.

### Phase 1 — Close one real improvement loop (P0; about 1-2 slices)

1. Select one recurring, user-relevant harness failure from the refreshed evidence, not a synthetic measurement cohort.
2. Trace exact signal, candidate/version, PM job, lane/attempt, test and QA receipts, Main acceptance, and later outcome. Inspect existing completion guards and actual receipt timestamps before diagnosing a title-match bug.
3. Refresh and resolve/classify the one currently supported actionable attribution gap if it remains; preserve historical unavailability without invented counters.
4. Define before-change measure, observation window, expected improvement, regression limits, and rollback before implementation.

**Exit:** one immutable receipt chain reaches later observed benefit or an honestly failed experiment; a seeded old/wrong/missing receipt cannot earn current success credit. The RSI scorecard identifies source freshness and does not mistake routing, acceptance, or a memory reference for measured learning.

### Phase 2 — Original skill updates and behavioral tests (P1; about 2 slices)

Implement the highest-value skill proposals above with an original bounded fixture pack. Start with the harness, prompt book, self-improvement, and input-trust QA owners; only update other skills when a demonstrated gap requires it.

**Exit:** baseline/current results for a useful task family plus safe adversarial, abstention, stale-input, missing-tool, and recovery variants; independent grader/QA, Main acceptance, revision/rollback evidence, and no authority widening. Skill publication requires explicit approval. No fixed ten-job minimum or automatic model promotion.

### Phase 3 — Reliability and efficiency pilots (P1; about 2 slices)

Run small, distinct-output pilots in parallel once the Phase 1 evidence contract is stable:

- **Resume:** interrupt a real long task, resume from existing artifacts, and prove no duplicate effects, lost acceptance state, or self-resumption after cancellation.
- **Efficiency:** compare artifact-first handoffs and bounded, cache-stable context on equivalent work. Report correctness and accepted outcome first; tokens/latency/retries only when authoritative.
- **Retrieval/provenance:** test negative and contradictory recall, capability/tool-schema mismatches, actual model identity, and the existing cooperative budget guard. Do not call it a native hard interceptor without separate runtime proof.

**Exit:** useful-task acceptance is retained, resource/latency change is measured or marked unavailable, failure/cancel paths pass, and no duplicate runtime is introduced. Stop a low-value or repeatedly failed pilot instead of rebuilding a control-plane benchmark.

### Phase 4 — Stronger-model and advanced-capability admission (P2/P3; separate decision)

Only after prior evidence is trustworthy, select a concrete capability gap. Test one new model route or tightly sandboxed tool capability using frozen comparable tasks, exact provenance, permissions, stop/cancel proof, and independent evaluation.

**Exit:** measured task benefit, bounded failure modes, least privilege, rollback, and explicit human acceptance. Do not enable public A2A, replace memory, add a second agent framework, run desktop control on the live host, or deploy autonomous self-modification as generic AGI preparation.
