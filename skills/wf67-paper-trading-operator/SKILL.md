# WF67 Paper Trading Operator

Use this skill when creating, validating, submitting, canceling, selling, reconciling, or reporting WF67 Alpaca paper-only trading requests, advisor-derived paper packages, paper feedback ledgers, kill switches, audit logs, SQL/JSON review evidence, or guardrails.

## Purpose

Run the Alpaca paper-only execution lane as a bounded simulation system. This skill never authorizes live trading, live endpoints, live credentials, money movement, account setting changes, close-position/liquidation endpoints, capital deployment, or promotion of paper results to live deployment.

A generated card is a recommendation object. A clean WF67 guard is a safety precondition. Randall's exact approval is the execution decision. These gates must remain separate in PM, cron, Telegram, and main-session surfaces.

## WF67 / WF87 / WF88 Authority Split

Keep these workflow roles separate:

- **WF67** is the paper execution guardrail and exact-order wrapper. It owns paper endpoint isolation, kill switch, audit/redaction, dry run, request artifact, exact owner approval metadata, submit/cancel/sell wrapper use, and post-action reconciliation.
- **WF87** is the paper-autonomy runtime governor. It may report runtime readiness, shadow maturity, daylight gates, routing-card state, and fail-closed conditions. It cannot approve, submit, cancel, sell, replace, or mutate any account/order state.
- **WF88** is the OS-wide learning, cleanup, route-contraction, and retired-surface owner. It may surface cleanup/readiness state and learning rows. It cannot approve execution, create order authority, widen paper autonomy, or bypass WF67.

Clean WF87 or WF88 proof can support preparation only. It may help create a card, explain a blocker, or route a repair. It never satisfies the exact approval requirement for execution.

If a surface says runtime ready, shadow mature, review-ready, owner-review candidate, near-deployment, or cleanup-ready, translate that as review context unless a current WF67 request artifact, fresh kill switch, guard validation, paper/live isolation proof, exact order terms, and Randall's exact approval are all present.

Do not let WF88 cleanup or WF87 runtime maturity convert into paper order authority. All paper execution still terminates at WF67.

## Execution Stop Line

No paper submit, cancel, sell, replace, modify, close-position, liquidation, brokerage/account action, endpoint mutation, credential use, money movement, or live action is allowed unless all of these are true:

1. Randall gives exact approval for the exact order terms.
2. A fresh short-lived paper kill switch exists.
3. WF67 guard validation passes after the approval.
4. The order uses the WF67 paper-only wrapper.
5. Paper/live isolation proof is current.
6. Redacted audit logging is enabled.
7. Post-action reconciliation is GET-only.
8. Live endpoints, live credentials, account settings, close-position/liquidation endpoints, and money movement remain blocked.

If any condition is missing, WF67 may only produce blocker proof and a review card.

## Blocked Actions

Stop immediately if any path implies:

- live endpoint, live credentials, live order, or live brokerage/account action
- money movement or account setting mutation
- close-position, liquidation, replacement, PATCH, PUT, transfer, or unwrapped POST/DELETE paths
- short sales, margin, leverage, options, crypto, multi-leg/bracket/OCO/OTO orders unless separately scoped and validated
- canonical portfolio/cash/risk-rule/sleeve/sizing mutation from a paper packet
- owner approval inferred from alert severity, score, validation, ranking, paper fill, packet quality, or cadence state
- probability, win-rate, expected-return, calibrated-score, or model-readiness claims while WF55 is not ready

Plain English: a paper sell is allowed only as a normal scoped paper sell order through POST `/v2/orders`; do not use close-position or liquidation endpoints.

## Assisted Attempt Versus Maturity Rep

Classify paper outcomes conservatively:

- `attempt`: submitted owner-approved paper order attempt
- `terminal_attempt`: attempted order with terminal broker state such as expired, canceled, rejected, or filled
- `filled_order`: broker reports fill/partial fill according to classifier
- `maturity_rep`: clean filled/reconciled proof category accepted by the workflow
- `filled_round_trip`: full buy/sell lifecycle with reconciliation proof

Expired, unfilled, rejected, canceled, unresolved, or stale attempts are telemetry only. They do not count as maturity reps and do not satisfy reconciliation maturity.

## Pre-Submit Checklist

Before any `--execute` submit/cancel/sell:

1. Confirm the source package: advisor packet, capital packet, explicit owner instruction, or existing scoped pilot artifact.
2. Confirm exact ticker, side, quantity/notional, order type, TIF, rationale, and risk check.
3. Confirm order scope: side is buy/sell; order type is limit/market; TIF is day or validated paper-only GTC; GTC is allowed only for limit orders; market/GTC is blocked.
4. Require explicit owner approval metadata for market orders and all execution actions.
5. Keep default pilot cap `qty <= 1` and estimated notional `<= $500` unless a validated full-scope artifact exists.
6. Run dry-run and guard validation first.
7. Create/verify a fresh short-lived kill switch only for the narrow execution window.
8. Re-run guard validation.
9. Execute only through the WF67 wrapper and exact paper endpoint.
10. Write/review redacted audit log and execution result.
11. Notify main session with ticker, side, qty/notional, order type/TIF, source artifact, guard status, kill-switch expiry, result, and next risk check.

## Post-Action Reconciliation

After submit/cancel/sell:

- reconcile order/position state through read-only paper APIs or existing reconciliation scripts
- update paper feedback ledgers when fill or material state changes occur
- preserve append-only outcome/feedback records
- if a paper outcome should later feed evaluation, create a proposal/sidecar artifact first; do not claim predictive performance

## Cron / WF68 Handoff Behavior

When a WF68 alert creates an advisor opportunity:

- WF68 may generate/recommend a WF67 paper package, but does not execute itself
- main-session handoff should report ready, blockers, or exact no-action status
- capital-package notifications should be concise and include proof paths
- expired kill switch outside execution window is a safe expected blocker; refresh only when actual scoped paper action is ready

## Blocked Automation

WF67/WF86/WF87 paper automation must not add:

- order resubmission automation
- cadence-triggered orders
- autonomous kill-switch creation or clearing
- autonomous phase promotion
- paper-to-live promotion
- owner approval inference from a clean card, score, alert, shadow decision, or cadence state

When in doubt, prepare the exact approval card and stop for Randall.

## Output Contract

For paper-action reports, include:

- conclusion: ready, executed, blocked, or no action
- paper/live boundary status
- source package and request artifact
- guard validation and kill-switch status
- order/result/reconciliation proof
- remaining risk or next action

When reporting a paper package that used SQL/JSON proof, include this line or equivalent:

```text
SQL/JSON proof supports internal review routing only; it does not approve paper execution.
```

## Closeout

Report ready/executed/blocked/no-action, paper/live boundary, source package, guard and kill-switch status, result/reconciliation proof, remaining risk, and next action.

## Final Boundary

If trade-grade readiness is false, freshness is below threshold, source-open is missing, exact owner approval is missing, kill switch is stale/missing, guard validation is stale/failing, endpoint is live/ambiguous, order terms are incomplete, or blocked mechanics are involved, stop at `blocked` or `approval card needed`; do not create an execution instruction.
